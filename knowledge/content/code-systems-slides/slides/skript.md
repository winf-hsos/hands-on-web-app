# Script: what the bits mean

These notes accompany the stagekit deck "what the bits mean". They explain the contents of the slides for reading afterwards and follow their order; build-up steps count as frames of their own in the player and in the export, so the references refer to frames.

## What this is about

An alphabet of colours knows colours, a text knows letters, and in between you need a rule that says which sequence of colours means which letter. That is exactly what a code is, and a code is nothing but a table that two parties have agreed on. The bits do not carry their meaning with them; they only get it when someone looks them up. That is why writing the table down is not paperwork, but half of the work.

## Part 1: the agreement is everything

**Who still knows what this means? (Frame 4).** The Rosetta Stone, 196 BC, the same text in three scripts. For fourteen centuries nobody could read the hieroglyphs in the top third. Not because the signs had been lost, they had been lying there in plain sight the whole time, but because the agreement had been lost: which sign means what. Only because the same text stood next to it in a known script did the mapping come back. In the 1820s Champollion did not decipher the stone so much as recover a table, one that had existed in people's heads two thousand years earlier and had then quietly gone out of use.

**What a code system is (Frames 5 and 6).** An agreed mapping of characters to sequences of symbols. That is the entire definition, and so that it does not hang in the air, a real table stands right next to it: ASCII, the oldest one still in daily use. Capital A is 65, B is 66, lower-case a is 97, and each of these numbers fits in one byte; the bits are written underneath. Only the number is stored. A letter as a shape exists nowhere inside the computer; it only comes back into existence when a program looks up the number and draws the matching shape. Two details repay a second look: the 65 is not A's position in the alphabet, since the first 32 slots of the table belong to control characters, which is why the letters start so late. And lower-case a is 97, a completely different number, not a variant of the same one. To the computer, `A` and `a` are two characters that happen to look related to us. Below the table, as a side note, stands the distinction, because it gets mixed up all the time in everyday speech: a code is not encryption, it hides nothing and is public so that both sides can use it. It is not compression: some codes happen to be economical, but making things smaller is not their purpose. And it is not program code, despite the shared name.

**The same A in three code systems (Frame 7).** If a code is a table, then there can be several, and there are. The same A is the bit sequence `0100 0001` in ASCII, a dot and a dash in Morse, three colours in a row in a colour alphabet. None of these versions is more correct than the others; which one applies is a matter of agreement.

**When the table is too small (Frames 8 and 9).** ASCII's 128 slots are enough for English and nothing else: no umlaut, no euro sign, no Greek, no Chinese, no emoji. This is the situation of every codebook that turns out too small, only worldwide: the table was too small, so a bigger one was agreed. Two steps are worth keeping apart here, because they are constantly confused. **Unicode** says which number a character has, and it assigns one to every character of every writing system, well over 100,000 of them. **UTF-8** says how that number is written down as bytes, and it does so with a varying length: whatever comes up all the time stays at one byte, rarer characters cost two, three or four. That is the same instinct that gives the E a single dot in Morse code, and it comes back in Part 3, where it causes trouble.

**Two tables, one message (Frames 10 to 12).** Now the mistake that costs the most time, and the reason the Rosetta Stone comes at the beginning. Two people type up the code table separately, and in one copy the entries for n and m are swapped. Everything else matches. The sender looks up n and sends its code word; the receiver looks up the same bits in its own table and finds a perfectly valid letter there, just not the one that was sent, so that `norm` turns into `morn`.

Technically, nothing goes wrong. No exception is raised, no checksum fails, no byte is corrupted. The receiver looks up every group of bits, gets a valid answer every time, and prints a word that looks like a word. This matters, because it runs against the feeling that computers speak up when something is wrong. They speak up when something is broken, and a wrong agreement is not broken: it is carried out correctly, and what comes out is clean nonsense.

## Part 2: build your own codebook

**How many positions per letter? (Frames 14 to 16).** Nothing new, just applied: the arithmetic comes from the number systems. Above the three columns it says what the calculation works with (the four colours of the alphabet) and what it is for (26 letters); without both, the red crosses would have no reason. With four colours, one position gives four code words, two positions sixteen, three positions sixty-four. Two are not enough for 26 letters, three are.

**The codebook (Frame 17).** 64 slots, each with its number of three positions in base 4; the space appears as a sign of its own, because otherwise it would be invisible. The 26 letters take 26 of them; space, full stop and the ten digits fit in without any change, and 26 slots stay empty. The picture says something the arithmetic hides: the table is much emptier than it feels. The 38 spare code words are not waste, they are stock. If you notice halfway through that you also want to send a space or a digit, the slots are already there, and nothing about the length changes. Which colour sequence belongs to which slot is your decision; the slots are given by the arithmetic, the assignment is the agreement.

**The same table, both directions (Frames 18 to 20).** Sending means looking up a character and getting a code word. Receiving means reading the same table the other way round. The code words on the slide are the ones from the codebook, `a = 000`, `b = 001`, `c = 002` in base 4. As long as no two characters share a code word, the reverse direction is unambiguous. In a program you will probably build the reversed dictionary once and put it next to the first; that is fine, and it is also the moment to be careful. Two separately maintained tables are two things that can drift apart, and you have just seen what drifting apart looks like. Better to derive the second from the first in one line than to type it twice.

**What is not in the table (Frame 21).** The occasion stands as a call above the slide, `send("good morning")`, and the codebook knows a to z and nothing else. Someone types a space, an umlaut, a digit, and that happens within minutes of the first test. Three ways out are defensible: add the character to the table, drop it before sending, or stop with an understandable message. Choosing none is not a way out, because then chance decides, or the program crashes in front of everyone. And beware of the comfortable thought that a space is nothing anyway. To the text it is a character like any other, and the receiver cannot invent a gap that was never sent.

## Part 3: where does a character end?

**A code that does not work (Frames 23 and 24).** The same layout as with the two tables, and that is the point: this time both sides have the **same** table, a = `0`, b = `01`, c = `10`, and it still goes wrong. The sender types "a c" and sends `010`. At the receiver, the same three bits appear twice, one above the other, once cut after the first bit and once after the second; under each cut it says which letters come out. Once "a c", once "b a", and both stick exactly to the agreement. The receiver sees a stream of bits without gaps. It does not know whether the first `0` was already a whole character or the beginning of a longer one. The problem is not that the code words have different lengths. The problem is that the code word for a is the **beginning** of the code word for b, and so nothing in the stream marks the boundary.

**The prefix trap (Frame 25).** The demonstrator [prefix trap](https://hands-on-computer-science.de/cs/en/items/prefix-trap/) lets you set the code words yourself, type a word and then see **all** the readings the receiver would have to choose between. Two tasks: bring the list down to one without giving all code words the same length, and build a code that produces especially many readings. If you manage the first, you have built a prefix-free code.

**Three ways out (Frame 26).** Not a recipe, but three workable paths, and none of them is the official one. **Fixed length** is the simplest: all code words the same length, and the receiver counts instead of guessing. A **separator** is what Morse uses, in the form of pauses between the letters. The third way is the most interesting: if no code word is the beginning of another, the lengths may stay different and the stream is still unambiguous, because as soon as what has been read matches an entry, it can only be that entry.

**What fixed length costs (Frame 27).** Why would anyone want variable length if it demands this much care? Because fixed length gives no discount to the letters that come up all the time. Two home-made codes are compared: three colour positions for every letter against two for the ten most common letters of English and four for the rest. An ordinary word gets shorter on average this way: for `experiment` it is 26 instead of 30 positions, so 2.6 instead of 3.0 per letter. On average, note, not always: a word made only of rare letters gets longer. Follow this thought to its end and you arrive at compression. Here it is enough to see that the choice is a choice and both answers cost something.

## Part 4: the same bits, other meanings

**Eight bytes, three readings (Frames 29 and 30).** So far it has all been about text, but no argument here had anything to do with text, and here is the proof: eight consecutive bytes from the middle of a photo of a parrot. Read as text, they are a capital M, a dollar sign, a capital E and five characters no editor can display; that is exactly what you see when you accidentally open an image in a text editor. Read as grey values, they are eight brightnesses. Read as audio samples, they are eight points on a wave. The bytes have no objection to any of these readings. Character salad is not a malfunction but a wrong agreement, carried out correctly.

**A pixel is three numbers (Frame 31).** Images are the same idea as text with a different table: per pixel three numbers from 0 to 255, for the red, green and blue share. The shares multiply rather than add, because every level of red can be combined with every level of green and blue: 256 times 256 times 256 is about 16.7 million colours, so 24 bits per pixel. The hex notation `#ECAB03` is not a different system, only a shorter version of the same three bytes, two places per byte. An RGB LED mixes its colour from the same three shares as a pixel on a screen, and a colour sensor measures it back in the same three channels.

**Who says which reading applies? (Frame 32).** If the bytes do not say it, someone else has to, and in practice there are three things. The **file extension** is the weakest of them, because renaming a file changes nothing about its content. A **header at the start of the file** is more reliable; a PNG, for example, always begins with the same eight bytes. And a **type field** in a message tells the receiver how to read the rest, so that it does not have to guess. That field is not a formality; it is this slide, built into a protocol of one's own.

## Part 5: codes without computers

**Four agreements without electricity (Frame 34).** The **barcode** turns bar widths into digits. **Sheet music** turns position and shape into pitch and duration. **Braille** turns six raised dots into a character, and Louis Braille designed it in 1825, at the age of sixteen. **DNA** turns three bases into an amino acid, and this table is the same in almost every living thing on the planet, which makes it both the oldest and the most widely deployed code system here.

**The same calculation, three times (Frame 35).** For two of them it pays to do the arithmetic. Braille is a six-bit code you read with your fingertips: each dot is raised or not, six dots, 2⁶ = 64 patterns. DNA has four bases and three positions per amino acid, 4³ = 64. And the colour alphabet has four colours and three positions, 4³ = 64. The coincidence is not one. Whenever you combine a fixed number of positions with a fixed number of states per position, you are doing the same calculation, whether the positions are fingertips, molecules or flashes of light.

**Write the table down (Frame 36).** Back to the stone: write the table down, and do it once, for both sides. Four steps: agree on a code that maps letters to colour symbols; write it down once and derive both directions from it; program sending and receiving; transmit a ten-letter word completely correctly, with a person setting the pace for now. The second step is where most people fail, and it does not look like failure, but like a wrong word.
