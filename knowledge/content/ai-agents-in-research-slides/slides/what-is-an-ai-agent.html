What an AI agent is, how it differs from a chatbot such as ChatGPT or Claude in the browser, and what that means when it works on your research paper. The one sentence to take home: an agent is a language model that runs tools in a loop until a goal is reached, so it can act in your folder, and that makes it useful and makes you responsible for every step it takes.
Five parts: the difference to a chatbot, what an agent is made of, one run of an agent on a paper in Quarto, what studies found about working with agents, and the rules for working with one.

A chatbot is like a consultant on the phone: it tells you what to do, and you do it. An agent is like someone you hand the keys to your office: it opens the files itself, reads them, changes them and runs programs. That is why it can do so much more, and why it matters what you let it do.
First the difference, which lies not in the model but in who takes the next step.

chatbot and agent

With a chatbot you write a prompt, the model writes an answer, and the next step is yours: you copy the R code into your script, run it, and paste the error message back. With an agent you give a goal, and the model calls tools itself, looks at the results and carries on until the goal is reached: it reads your script, runs it, sees the error and fixes it. Under the hood it can be the same language model; the difference is what is built around it.

a working definition

an ai agent runs tools in a loop to achieve a goal.
after Simon Willison, 18 september 2025
Three words carry the definition. Tools: the agent can read and write files, run programs and search the web. Loop: it looks at what a tool returned and decides on the next step itself. Goal: you say what you want, not how to get there. Anthropic describes agents in almost the same words, as language models that use tools based on feedback from their environment in a loop.
Now the inside of an agent, built up step by step, with the goal of getting feedback on the introduction of a paper.

the goal and the model

At the start a goal and a language model. On its own the model can only produce text; it cannot open a file. Then the tools: read, edit, write, bash for running programs such as R or Quarto, and web search. The model only writes down which tool it wants to call with which arguments; the program around it carries out the call on your computer. Then the loop: the result of every call goes back to the model, which thinks, acts again and observes again. In research this pattern is called ReAct, and it is the core of every agent.

memory, plan and instructions

Everything the agent knows during a run sits in its context window: the goal, every file it has read and every result. It fills up with each file, and when it is full, the agent has to summarize or forget. The plan is a list the agent writes and ticks off, a tool like any other. Instructions in text files are loaded at the start: a file called AGENTS.md says what the agent should know about the project, and commands are prepared instructions for recurring tasks, such as how to give feedback on a paper. In the last step everything is together, and only the loop is highlighted, because it is what makes the model an agent.

the harness

Everything around the model is called the harness, like the harness that hitches a horse to a cart: the model provides the power, the harness steers it. It runs the loop, carries out the tool calls, manages the context window, loads AGENTS.md and the commands, and asks you for permission. OpenCode, Claude Code and Codex are harnesses, and many of them let you choose the model. An AI agent is a language model plus a harness.
Now one run of an agent on a paper in Quarto, as its log shows it, and the setting that decides what it may do without asking.

one run, as the log shows it

You give a goal in one sentence. The agent reads the central file of the paper and finds that the sections live in files of their own, so it reads the introduction. Then it answers: the research question stands in the second paragraph instead of at the end. Nothing has changed in your files so far. Only when you ask it to move the question does it want to edit the file, and the harness stops and asks you: allow once, allow always, or reject. Before you allow, you see the change as a diff, line by line.

what it may do without asking

"permission": { "edit": "ask", "bash": "ask" }
in the settings of the harness, here opencode.json
reading is allowed, and changing a file or running a program waits for your yes.
The harness has settings for what the agent may do on its own. With these two lines, it may read your files freely but has to ask before it edits a file or runs a command in the shell. You can loosen this, for example allow it to always run R, but the safest start is to let it ask and to read what it wants to do before you say yes.
What do studies say about working with agents? Three findings, each with its source, and each with a lesson for your own work.

feeling faster, measured slower

Becker et al. (2025), METR: 16 experienced developers, 246 tasks in their own projects, early-2025 tools
feeling faster is not the same as being faster, so judge an agent by what it delivers.
In a randomized trial by METR, experienced software developers worked on real tasks in their own projects, each task randomly with or without AI tools, mostly Cursor with Claude. Before, they expected to be 24 percent faster with AI; afterwards they believed they had been 20 percent faster. Measured, they took 19 percent longer. The tools have improved since, and in February 2026 METR wrote that its newer data hint at a speed-up but that it can no longer measure it reliably with this design. What remains is the gap between feeling and measuring.

agents stop at simple analyses

on 12 data sets with questions from published studies, language models and agents mostly chose basic analyses, and fewer different ones than expert analysts.
Gu et al. (2024), BLADE: benchmarking language model agents for data-driven science, Findings of EMNLP 2024
which variables, which groups and which method stay your decisions.
The BLADE benchmark gives models and agents a data set and a research question from a published study and compares their analysis decisions with those of expert analysts: which variables, how they are transformed, which model. The models knew a lot about the subject, but they mostly stopped at basic analyses; agents that could work with the data did better but still made fewer and less varied decisions than the experts. For your paper this means: let an agent write and run the code, but decide yourself what is analysed and how.

instructions hidden in what it reads

an agent treats text in a web page or a file as possible instructions, and an attacker can hide some there.
Greshake et al. (2023), not what you've signed up for: indirect prompt injection
what an agent reads can steer it, so let it ask before it acts.
A language model cannot reliably tell your instructions apart from text it reads along the way. Greshake and colleagues showed that a web page or a document can contain hidden instructions that make an assistant do something else, for example send data somewhere. This is called indirect prompt injection, and there is no complete protection against it yet. That is one more reason to keep the permission settings strict and to read what an agent wants to do before you allow it.
the agent reports: “i fixed the analysis, everything runs.” what do you do?
  1. trust it and go on
  2. read the change, run it
  3. ask it if it is sure
  4. start again without ai
Read the change and run it yourself. That the code runs says nothing about whether it computes the right thing, and asking the agent whether it is sure only gets you another confident answer. Starting again without AI throws away work that may well be good.
To finish, five rules for working with an agent on a research paper.

five rules

give it a goal and the context it needs.
let it ask before it changes a file or runs a program.
read every change before you accept it.
run the code yourself and check one number by hand.
keep personal data out, and answer for the result yourself.
A goal and context: what the paper is about, which file, what you want back. Permissions: reading is fine, changing waits for your yes. Every change is a diff you read. The code you run yourself, and one number you count by hand. And whatever an agent does in your folder, it does on your behalf: names, free-text answers with personal details and files you may not share stay out, and the paper is yours.
an agent runs tools in a loop until a goal is reached, so it can work in your folder, and you decide what it may do and check what it did.
That is the whole input in one sentence. Try it on your own paper: ask an agent for feedback on your introduction, and check every point it makes before you change anything.
